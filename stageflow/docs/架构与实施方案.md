# StageFlow 架构与实施方案

2026-10-03。本轮先完成项目命名、场地模型与程序结构方案，后续按此实现可操作示例。

## 1. 空间与观察视角

从俯视看，北门在房间北墙，南门在南墙，电动幕布位于房间正中，横贯东西。它将一个房间等分为两个区域。

~~~text
                    北
          ┌────── NPC 北门 ──────┐
          │                     │
          │   北侧演绎 / 备场区  │
          │   N1  N2  N3  N4    │
          │                     │
          ├══════ 电动幕布 ══════┤
          │                     │
          │    南侧玩家区       │
          │  P1  P2  P3  P4  G  │
          │                     │
          └────── 玩家南门 ──────┘
                    南
~~~

坐标统一为 X 向东、Y 向上、Z 向南。房间中心为原点，幕布在 Z=0，北门在 Z=-depth/2，南门在 Z=depth/2。

尺寸先使用宽 8、深 10、高 3.2 的示意值，单位可按米理解，尚非实际场地测量。两个区域进深各为 depth/2。门居中只是默认值，门宽与位置单独配置。

幕布开合方式还没有确认。第一版可采用左右对开，CurtainModel 只保存开度 0 到 1；显示策略以后可以换成上卷，流程层不用改。尚未达到可通行开度时，不让人物从幕布穿过去。幕布全宽与门宽分开配置。

提供两个主要视角。导演视角从斜上方看全场，可观察北侧备场；玩家视角从南侧看北侧，闭幕时不能看见幕后的演员、气泡和道具。导演视角看到的备场不是故事中玩家角色已知道的信息。幕布不默认隔音，需要说明的幕后动作仍由脚本安排。

## 2. 技术选择

Three.js 负责几何、光照、相机与火柴人显示，TypeScript 负责类、接口和数据类型，Vite 负责本地开发与模块构建。页面控件和气泡使用 HTML/CSS，气泡按人物头顶世界坐标投影，字体保持可读。

第一版不需要后台、账号服务或数据库。也不需要复杂骨骼动作，人物先有站、坐、转向、走动、抬手与递物几个姿态。

后续需要精细模型时，替换人物显示适配器为 GLB 模型即可。人物 ID、位置、朝向、动作接口和流程数据保留。

## 3. 面向对象职责

| 对象 | 职责 | 不承担的职责 |
|---|---|---|
| RoomModel | 尺寸、区域、门位置、可行走范围 | 台词与灯光渲染 |
| ActorModel | 人物 ID、位置、朝向、姿态、所持道具 | 直接创建 DOM 或调用音频 |
| CurtainModel | closed/opening/open/closing 状态、开度、操作进程 | 决定哪一幕开始 |
| SceneDirector | 当前步骤、分支选择、推进条件与步骤快照 | 绘制人物与气泡 |
| ActionRunner | 执行走位、转身、开幕等动作，报告完成 | 阅读剧本或选择角色动机 |
| ThreeRoomView | 按状态显示房间、门、幕布和物件 | 保存第二份业务状态 |
| ActorView | 火柴人模型与姿态显示，可换模型适配器 | 判断玩家选择 |
| DialoguePresenter | 气泡、人物名、当前说话者突出与遮挡处理 | 控制人物走位 |
| AudioService | 音频加载、播放、暂停、停止，报告结束/失败 | 自己推进剧情 |
| PlaybackPanel | 按钮、进度、视角、分支选项 | 自行修改人物坐标 |
| App | 创建对象、注入接口、连接 UI 与流程 | 堆放所有业务实现 |

数据和简单函数保留为配置或工具函数。核心有状态对象面向对象组织，避免为了形式把每个数字、每句台词都做成一个类。九个人共享同一个 ActorModel；机器人等动作差异由配置与策略表达。

## 5. 用流程数据驱动，不按动画时长硬跳

每一步有 ID、参与者、目标位置、动作、台词、完成条件和下一步。示例动作为 EnterDoor、MoveTo、TurnTo、Sit、Speak、OpenCurtain、CloseCurtain、WaitForPlayer、ChooseBranch。

NPC 入场使用北门，玩家入场使用南门。当前第一幕正文以玩家已经坐好为开场；流程示例可先独立展示入场，正式第一幕载入已落座的初始状态，两者不混作剧本原有情节。

备场步骤结束后开始开幕；CurtainModel 报告开幕完成，才转到演绎步骤。说话与手势可以并行，台词结束或演示者手动确认以后再推进。玩家回应位置进入等待，选择分支或点击继续才运行下一步，不能按音轨时间自动认定玩家答应。

自动播放只是已明确步骤的推进模式。每个等待、分支点照常停住。

暂停同时冻结运动、幕布、流程推进和音频。上一步用步骤快照恢复人物、道具与幕布状态，停止旧音频和旧动作，避免上一段声音继续播放。切换分支从分支节点的基准状态开始。

## 6. 气泡与语音

每人头顶保留 ID；当前说话者显示一个主要气泡，并突出其身体颜色。同一时刻多句台词按顺序呈现，不把九个大气泡重叠。视角移动时气泡跟随投影，位置冲突时错开或用侧边台词面板兜底。

台词条目保存 dialogueId、speakerId、text 和可选 audioKey。录音或合成语音均作为资源提供，不绑定模型。未来为 N1 至 N4、P1 至 P4、G 各配对应音色；演示玩家语音明确标为示例回答。

点击播放后开启音频。语音存在时气泡显示时间由播放进度决定，动作结束与语音结束按当前步骤定义合并；语音缺失或播放失败时保留文字、允许手动继续，不让流程卡死。

## 7. 第一版实施范围

第一步实现一间房、两扇门、九个火柴人、四对颜色与 G 单独颜色，带 ID 和视角切换。

第二步实现独立的 CurtainModel 与开合显示；人物走位遵守两区、门与幕布边界。

第三步接五到八个短步骤，演示玩家南门入座、NPC 北门备场、幕布打开、NPC 台词与动作、玩家回应等待、G 加入同桌，以及演出后的收幕。

第四步加入逐步/自动播放、重播、快照恢复、气泡和分支。第一版先不生成九套语音，但保留接口。

顺序最终按一个简短场景串起来。全长第一幕与精细模型在基础示例可操作之后再接入。
